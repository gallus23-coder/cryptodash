# Decision Log UI (Milestone 7, Part B) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Decision log tab (design §8.3) against Part A's API: a timeline with one row per hourly cycle, a scorecard at the top, click-to-expand detail, and basic filters — served as a static vanilla-JS page from the existing `dashboard.js`/`src/server/app.js`, not v1's `public/index.html`.

**Architecture:** Part A's API has every endpoint the expand view and scorecard need, but nothing that lists *cycles* — `GET /api/decisions` only returns rows that have a decision, which means a `risk_off` cycle with zero candidates (the overwhelming majority of real cycles so far) is invisible to it. Design §8.3 explicitly wants the timeline to show those cycles too ("Code writes the plain line for non-Claude events (no call, stop hit, fallback)"), so Task 1 adds `GET /api/cycles`, reading `cycle_log` directly and generating that plain-English line in code. The page itself is one static HTML file plus a small vanilla-JS module per concern (timeline, expand view, scorecard) — no build step, no framework. **Every browser-loaded JS file in this plan uses the `.mjs` extension**, decided once here rather than discovered mid-plan: Node's test runner treats a plain `.js` file as CommonJS by default (this repo's `package.json` has no `"type": "module"`), so a module using `export`/`import` needs either `.mjs` or a `type: module` field — `.mjs` is unambiguous to both Node and browsers regardless of any `package.json` setting, so it's used everywhere from the start. The data-shaping logic each module depends on (one-liner generation, R formatting, outcome formatting, row classification) is extracted into plain functions in `format.mjs` and unit-tested with `node --test`; actual DOM rendering isn't unit-tested, since no browser is available in this environment — see the exit check for what that means for sign-off.

**Tech Stack:** Express (serving static files + the existing Part A API), vanilla JS ES modules (`.mjs`, no bundler), `node --test` (native ESM support) for the extractable pure logic.

**Spec:** `docs/v2-design.md` §8.3 (Decision log — timeline, expand view, filters, scorecard), §8.7 (Tailscale-only access, dashboard password already wired in Part A). `CLAUDE.md`'s "Front-end: vanilla JS... (no CDN)".

**Depends on:** `docs/superpowers/plans/2026-11-19-decision-log-api.md` (Part A — `GET /api/decisions`, `GET /api/decisions/:cycleId`, `GET /api/scorecard`, `dashboard.js`, password middleware). All merged and pushed.

## Global Constraints

- No CDN, no build step, no framework — static files served directly, `.mjs` modules loaded via `<script type="module">`.
- The password header (`X-Dashboard-Password`) must be sent with every fetch from the browser — there is no login/session UI yet (Part A deferred that); this plan adds the minimal thing that makes the page usable: a password prompt stored in `sessionStorage`, re-sent on every API call.
- Every API call must carry `mode=paper` explicitly from the client (not rely on the server's default) — matching design §8.4's "every screen has a Paper / Live / Both filter"; this plan hardcodes the mode selector to `paper` only (no live mode exists yet) but wires the parameter through so adding a selector later doesn't require touching the fetch calls.
- `public-v2/` is new, separate from v1's `public/` — v1's `index.html` is untouched.

## Interpretation decisions

- **A new `GET /api/cycles` endpoint is added in this plan (not originally in design §9's list), because the design's own timeline requirement ("one row per hourly cycle") has no endpoint that can produce it.** `GET /api/decisions` is a per-*decision* list — a cycle with zero candidates (the actual shape of every real cycle so far, since the market has been `risk_off`) produces zero rows there and would be completely invisible on the timeline. `cycle_log` has exactly the one-row-per-cycle shape the timeline needs, including cycles with no candidates at all.
- **The plain-English one-liner for non-Claude events is generated by a pure function (`buildCycleOneLiner(cycleRow)`) server-side, not in the frontend.** Design §8.3: "Code writes the plain line for non-Claude events... Claude writes it for its own decisions." For a Claude-involved cycle, the frontend's expand view uses the stored `plainReason`/`marketNote` fields already in `decisions`; for everything else (`candidatesCount === 0`, or a `cycle_log.error` is present), the server generates a fixed, templated line — no LLM call needed, keeping generation server-side and testable without a browser.
- **No login/session page — a single `sessionStorage`-backed password prompt.** Building the full password-entry screen design describes (part of Settings, §8.4) is out of scope for the Decision log tab alone; this plan's minimum viable version asks once per browser session via `window.prompt` if no password is cached.
- **Filters are scoped to `regime` only, not the full design §8.3 list (coin, setup, regime, action, "Claude overrode default", result).** `GET /api/cycles` filters cheaply on `cycle_log`'s own columns; `coin`/`setup`/`action` require a semi-join against `candidates`/`decisions` per cycle, real additional API surface deferred to a follow-up task — almost every cycle has zero candidates right now, so those filters would have nothing to filter yet.
- **All browser-loaded `.mjs` files live flat in `public-v2/js/`** — `api.mjs`, `format.mjs`, `scorecard.mjs`, `timeline.mjs`, `expand.mjs` — with `format.mjs` holding every pure, testable function and the other four holding only DOM wiring that imports from it.

## Review Focus

- A cycle with `candidatesCount: 0` must render a clear, correct one-liner ("No candidates this hour") on the timeline — not a blank row, not an error, not "undefined". This is the common case for every real cycle logged so far, so it's also the first thing a real user of this page will see.
- A cycle with `cycle_log.error` set (a caught exception from `runCycle`'s try/catch, per milestone 5) must render distinctly from a normal "no candidates" cycle — conflating "nothing happened" with "something broke" would hide real operational problems.
- The scorecard's `notEnoughData: true` state (guaranteed true for all real data right now — zero diverged decisions exist yet) must render a clear "not enough data yet" message, not `NaN`/`undefined`/a raw `0` that looks like a real (bad) score.
- Every fetch call must include the password header; a `401` response (wrong/missing/expired password) must prompt again, not silently show an empty page that looks like "no data."
- The expand view for a candidate with a real trade (has `.trade`) vs. one that was only shadow-tracked (`.trade: null`, only `.shadow_*` fields on the candidate) must each show the right outcome — showing blank for a skipped candidate's outcome would contradict design's explicit "the outcome (trade P&L or shadow P&L if skipped)."

```js
function buildCycleOneLiner({ regimeLabel, candidatesCount, openedCount, closedCount, error }) {
  if (error) return `Problem this hour: ${error}`;
  if (closedCount > 0) return `Closed ${closedCount} position${closedCount === 1 ? '' : 's'} (${regimeLabel}).`;
  if (openedCount > 0) return `Opened ${openedCount} position${openedCount === 1 ? '' : 's'} (${regimeLabel}).`;
  if (candidatesCount > 0) return `${candidatesCount} candidate${candidatesCount === 1 ? '' : 's'} found, none taken (${regimeLabel}).`;
  return `No candidates this hour (${regimeLabel}).`;
}

function getCycleLogFiltered(db, { mode = 'paper', from, to, regime, limit = 100 } = {}) {
  const clauses = ['mode = @mode'];
  const params = { mode, limit };
  if (from !== undefined) { clauses.push('ts >= @from'); params.from = from; }
  if (to !== undefined) { clauses.push('ts <= @to'); params.to = to; }
  if (regime !== undefined) { clauses.push('regime_label = @regime'); params.regime = regime; }

  return db.prepare(`
    SELECT ts, mode, regime_label AS regimeLabel, candidates_count AS candidatesCount,
      opened_count AS openedCount, closed_count AS closedCount, duration_ms AS durationMs, error
    FROM cycle_log WHERE ${clauses.join(' AND ')} ORDER BY ts DESC LIMIT @limit
  `).all(params).map((row) => ({ ...row, oneLiner: buildCycleOneLiner(row) }));
}
```

Add `buildCycleOneLiner, getCycleLogFiltered` to `module.exports`.

```js
'use strict';

function getPassword() {
  let password = sessionStorage.getItem('dashboardPassword');
  if (password === null) {
    password = window.prompt('Dashboard password:') || '';
    sessionStorage.setItem('dashboardPassword', password);
  }
  return password;
}

export async function fetchJson(path, params = {}) {
  const query = new URLSearchParams({ mode: 'paper', ...params }).toString();
  const url = `${path}?${query}`;
  const password = getPassword();

  const res = await fetch(url, { headers: { 'X-Dashboard-Password': password } });
  if (res.status === 401) {
    sessionStorage.removeItem('dashboardPassword');
    const retryPassword = getPassword();
    const retryRes = await fetch(url, { headers: { 'X-Dashboard-Password': retryPassword } });
    if (!retryRes.ok) throw new Error(`request failed: ${retryRes.status}`);
    return retryRes.json();
  }
  if (!res.ok) throw new Error(`request failed: ${res.status}`);
  return res.json();
}
```

Create `public-v2/js/format.mjs`:

```js
export function formatR(value) {
  const sign = value >= 0 ? '+' : '-';
  return `${sign}${Math.abs(value).toFixed(2)}R`;
}

export function formatScorecardMessage({ notEnoughData, divergedCount, claudeMeanR, defaultMeanR, days }) {
  if (notEnoughData) {
    return `Not enough data yet (${divergedCount} override${divergedCount === 1 ? '' : 's'} so far — need about 100).`;
  }
  return `Over the last ${days} days: Claude averaged ${formatR(claudeMeanR)} per overridden trade vs ${formatR(defaultMeanR)} for the untouched default.`;
}
```
